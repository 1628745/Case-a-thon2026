# LAB_PLAN: "Try it" live demo page

Phase 2 of the Case-a-thon 2026 project. Phase 1 (the study, results and the narrative site in `docs/`) is DONE; see PROGRESS.md, DISCOVERY.md, DECISIONS.md. This plan adds one new page to the site, `docs/lab.html`, where anyone can load a LaDe-format delivery file, optionally inject the same defects we studied, and watch the frozen Guard and a gradient-boosted model train **in their own browser**, then compare Guard off vs Guard on.

**Pitch line for the judges:** "Bring your own delivery data. Our exact pipeline runs in your browser, nothing is uploaded anywhere, and the Guard's settings were frozen on Chongqing, so whatever you see on a new city is an honest out-of-sample test."

---

## 0. Hard constraints

1. **Never push and never touch the live site.** Work on a local branch `live-demo`. No `git push`, no merge into `main`, no GitHub Pages or `gh` changes. The user tests on localhost first and publishes themselves.
2. **Static only.** The page must work on GitHub Pages (no server code). All compute happens client-side in a Web Worker running Pyodide.
3. **Data never leaves the browser.** No network calls with user data, no analytics. Say so on the page.
4. **Don't break the existing site.** The narrative page (`index.html`, `app.js`, `style.css`) was redesigned by a teammate (three parts: `#poisons`, `#built`, `#analysis`; D3 charts; keyboard shortcuts 1-4). Only allowed changes there: add a "Try it" link to the header nav (and optionally a key `5`), plus shared CSS that doesn't change existing rules. A smoke test of `index.html` must pass at the end exactly as before (no console errors, all charts render).
5. **No redistribution.** Never ship LaDe rows in `docs/`. A built-in sample must be synthetic (generated by a script, labeled "synthetic") and the cached fallback holds aggregates only.
6. **No tuning on uploaded data.** Guard settings come from the frozen `config.yaml` `guard:` block (tag `guard-v1-frozen`). Show results honestly, including when the Guard doesn't help.

## 1. Feasibility facts (verified 2026-10-23)

- Pyodide **0.29.4** ships lightgbm **4.6.0**, numpy 2.2.5, pandas **2.3.3**, scikit-learn 1.7.0, pyyaml 6.0.2 (https://pyodide.org/en/0.29.4/usage/packages-in-pyodide.html). Load from `https://cdn.jsdelivr.net/pyodide/v0.29.4/full/` (pin exactly).
- The local `.venv` has pandas 3.0.6 and LightGBM 4.7.0. **Browser Python code must run on both pandas 2.3 and 3.0** (avoid pandas-3-only behavior; don't rely on the default string dtype or on copy-on-write semantics). Test in both.
- WebAssembly is single-threaded and slower than native: use `n_jobs=1` and the "Quick" model budget below. First load downloads roughly 25-40 MB (Pyodide, numpy, pandas, scipy, lightgbm), cached by the browser afterwards; start preloading as soon as the page opens.

## 2. User flow (one page, five steps, left-to-right progress bar)

1. **Load data.** Drag-and-drop or file picker for a LaDe delivery CSV (columns as in `delivery_cq.csv`). Options: "Use synthetic sample" (always works) and a note suggesting the real Yantai file `delivery_yt.csv` for the demo. Show file name, size, rows.
2. **Check data (audit).** Schema validation with friendly errors (missing columns, unparseable times, fewer than 6 full weeks). Detected date range and weeks, rows per week (small bar chart), couriers, areas, and the observed-issue counts from `src/audit.py` (duration <= 0, > 12 h, same-minute bursts, duplicate ids, GPS fix age, courier-to-stop distance > 30 km). Time format: same `MM-DD HH:MM:SS` handling as `prep.py`, with a year selector (default 2022).
3. **Poison it (optional).** The "poison dial": presets **Clean as uploaded**, **Sloppy couriers 20%** (default), **Stale feature store**, **Sloppy + stale**, **Unseen: early scans 15%**. Advanced: a slider for the sloppy-courier share (0-60%) and checkboxes per mechanism. Explain each in one sentence.
4. **Train.** Button "Run the experiment". A Web Worker runs the pipeline with a live step log and progress bar (loading Python, preparing features, injecting, training each model, scoring), elapsed time, and a Cancel button (terminates the worker).
5. **Results.** See section 4.

## 3. Experiment design per run (mirror the study, compressed to one split)

- **Weeks:** week 0 = the Sunday on or before the earliest accept date. Use only full weeks. Require >= 6 full weeks (4 training + at least 1 earlier week for history features + 1 test), else refuse with a clear message.
- **Split:** test week = the last full week; training window = the 4 weeks before it; history features (14-day courier and area means, open workload, distance) are computed exactly as in `prep.py` / `walkforward.py` from data before each row's day.
- **Models:** the same features (`config.yaml features`) and objectives (median `l1`, promise P80 `quantile`). Two budgets:
  - **Quick (default):** `n_estimators=150, num_leaves=31`, other params from config; training rows capped at 120,000 by sampling whole couriers (seeded), recorded and shown.
  - **Full:** the study's settings (300 trees, 63 leaves), no cap; warn that it can take several minutes.
- **Runs when a defect is selected (3 model pairs):**
  1. *Reference*: data as uploaded, Guard off.
  2. *Degraded, Guard off*: injected training data and history features.
  3. *Degraded, Guard on*: same injected data with the frozen Guard (L1 flags, L2 weights, L3 conformal promise + defer).
  Scoring always uses the uploaded (un-injected) test-week durations, as in the study. Recovery % = (degraded off - guarded) / (degraded off - reference), shown only when the gap is larger than a noise floor (gap > 1% of reference MAE); otherwise say "the defect did not measurably hurt this dataset".
- **Runs for "Clean as uploaded" (2 model pairs):** Guard off vs Guard on on the data as uploaded. Headline = "cost of the Guard on your data" plus what L1 flagged (real, observed issues).
- **Injection schedules compressed to the window:** reuse `src/degrade.py` mechanisms with the same parameters, but map the ramp onto the available training weeks (bulk-scan probability rises linearly from 0.10 to 0.90 across the 4 training weeks; duplicate re-uploads start in the window's second half with probability 0.8; stale features freeze at the start of the training window; early scans at 40-70% of true duration on a disjoint 15% of couriers). Defects touch training data and history features only, never test labels.
- **Seed:** fixed default (0), editable in Advanced; every result shows the seed and settings used.

## 4. Results panel (what the user sees)

**P1: must have**
- KPI cards: MAE (min) for each run, recovery %, promise-miss rate, average promise width, deferral rate, P90 error. Guard off vs on side by side, using the site's existing color tokens.
- Bar chart: MAE and P90 for reference / degraded off / degraded on.
- **Guard activity:** L1 flags by type (bursts, duplicates, non-positive, far, GPS age), rows quarantined, share of training weight down-weighted, effective training size.
- **Detector scorecard** (only when injected): confusion counts, precision, recall, false-positive rate (positive = injected record), using the injector's labels only for scoring.
- **Source reputation:** histogram of courier reputations, plus a table of the 10 lowest-reputation couriers (hashed short IDs, never raw IDs) with records, flag rate and disagreement z-score. When injected, mark which ones were actually sloppy.
- **Run facts:** rows used, weeks, sample cap, seed, model budget, Guard config hash (from `config.yaml`), training seconds per model, prediction latency (ms per package), Pyodide/LightGBM versions.
- Honest-result banner: green if the Guard recovered most of the gap, neutral if there was nothing to fix, red if the Guard made things worse, with one plain sentence.

**P2: should have (high value for judges)**
- **Explain a prediction:** pick a test package (dropdown of 5 auto-chosen examples: a typical one, one from a sloppy courier, a deferred one, a rare area, a long delivery). Show a feature-contribution waterfall Guard off vs Guard on using LightGBM `pred_contrib=True` (exact TreeSHAP), and the L3 health card with Approve/Defer reason. This visibly shows the inflated courier-history feature being neutralized.
- **Human in the loop:** in the reputation table, a "Release this courier" toggle (dispatcher overrides the Guard). Rerun applies the override (reputation = 1, flags kept) and the results update, showing oversight changing the model.
- **Downloads:** `lab_report.json` (all metrics, settings, versions, timings), `quarantine.csv` (row number in the user's file, courier hash, reasons; nothing else), and `model_card.md` (intended use, data, metrics, limits, Guard settings). All generated in-browser.
- **Compute vs human effort:** training seconds and ms/prediction next to estimated dispatcher minutes (deferred packages x 45 s, labeled as an assumption).

**P3: if time allows**
- **Live dose-response sweep:** "Sweep the dial" runs 0 / 20 / 40 / 60% sloppy shares (Quick budget) and draws MAE off vs on as the dose rises, reproducing the study's dose-response on the user's data.
- **New-city result card on the main page:** if the native Yantai run (step L7) is ready, add one small card in `#analysis` linking to the lab: "Guard settings frozen on Chongqing, applied to Yantai: X% recovered". Only add it if it fits the existing design; otherwise put it on the lab page only.

## 5. Architecture and files

```
docs/lab.html                 # the page (same header/nav/fonts/tokens as index.html)
docs/lab.css                  # lab-only styles, built on style.css variables
docs/lab.js                   # UI, charts (reuse the D3 version index.html already loads), worker messaging, downloads
docs/lab-worker.js            # Web Worker: importScripts Pyodide 0.29.4, loadPackage(numpy, pandas, lightgbm), runs guardlab
docs/py/guardlab/__init__.py  # browser package: generated copies/adapters of src core logic
docs/py/guardlab/*.py         # prep (time parsing, features), degrade (injectors), guard (L1/L2/L3), model, run_lab (orchestration)
docs/py/lab_config.json       # generated from config.yaml (features, model params, guard block, degrade params, config hash)
docs/data/lab_cached_yantai.json   # aggregates only: native-pipeline result for the Yantai preset (offline fallback + parity)
docs/data/lab_sample.csv      # SYNTHETIC LaDe-shaped sample (generated, labeled synthetic, a few MB at most)
scripts/build_lab.py          # copies/adapts src core into docs/py/guardlab, writes lab_config.json, generates the synthetic sample
scripts/lab_native.py         # runs the same lab experiment natively (src + .venv) for parity and the cached fallback
tests/test_lab_parity.py      # docs/py/guardlab vs src on a small synthetic frame (same features, flags, weights, injections)
tests/e2e_lab.py              # Playwright end-to-end test of lab.html + smoke test of index.html
LAB_PROGRESS.md  LAB_TESTING.md
```

- **Single source of truth.** Core logic stays in `src/`. Refactor only if needed so the core functions avoid file I/O, `yaml`, `subprocess` and `pyarrow` at import time; `scripts/build_lab.py` copies them into `docs/py/guardlab/`. Phase-1 tests must still pass after any refactor (`pytest -q`).
- **Worker protocol:** messages `{type: "load"}`, `{type: "audit", file}`, `{type: "run", options}`, `{type: "cancel"}`; worker posts `{type: "progress", step, pct, msg}`, `{type: "audit_result", ...}`, `{type: "result", ...}`, `{type: "error", msg, detail}`. Transfer the file as an ArrayBuffer and write it into Pyodide's virtual filesystem; parse with `usecols` and explicit dtypes to save memory.
- **Big files:** after parsing, if there are more than 400,000 rows, keep the last 7 full weeks (6 + 1 spare) before sampling, and tell the user. Chongqing (145 MB) must either complete or fail with a clear message, never hang.
- **Fallback:** if Pyodide fails to load (offline, CDN blocked), offer "Show cached Yantai result" from `lab_cached_yantai.json`, with a visible "cached, not live" badge.
- **Design:** read `docs/index.html` and `docs/style.css` first and match them: fonts (Big Shoulders Display, Overpass), CSS variables (`--floor`, `--panel`, `--ink`, `--ref`, `--stale`, `--lq`, `--comb`, `--unseen`, `--tote`, `--pass`, `--fail`), light/dark theme toggle, focus styles. Works at 1440x900 (projector) and 390 px wide. Pin any new CDN script to an exact version.
